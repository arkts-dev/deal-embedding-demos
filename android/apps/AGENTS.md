Always deliver a complete end-to-end user story through one clear user-facing facade: with setup complete, open the app, discover useful help, tap to use it, change an input, observe the result and reopen it. Inspect owns implementation details and accountable evidence. Keep it reachable before generation and after failure, scoped through public trace/experience observations. Returning from Inspect must not retry failed inference; recovery is an explicit user action. Competing legacy entrances, extra engineering confirmations or instructions to avoid the wrong button are integration defects, not follow-up suggestions. Verify the actual installed journey before declaring completion; developer setup does not count. Capability descriptions must specify executable argument semantics and prerequisites, not just types. Reject malformed/empty baskets and invalid periods rather than supplying successful defaults; package availability must account for shared component stock.

Treat functional acceptance and visual acceptance separately. Ordinary screens contain the user's task, controls, concise status and necessary consent—not implementation narratives. Inspect owns technical details; setup/access controls do not occupy the task canvas. Read the active design guidance before changing native or generated presentation. Capture real device states and review their screenshots for hierarchy, density, action visibility and controls/result proximity. A successful build, UI-tree assertion or working tap is not a visual review. When images cannot be reviewed, report visual acceptance as open rather than declaring UI completion.
